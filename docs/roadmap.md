# Immersive toolkit roadmap (VR Link + Skylight Fusion tools)

Goal stated by Nelson (Oct 2026): consolidate VR Link and the Skylight Fusion macros into an easy-to-use, distributable solution for immersive filmmakers; Resolve first, Premiere later. Product framing and tiers (Kalyx View / Canvas / Theatre) are in "Velaria MVP and product roadmap"; this doc is the engineering backlog.

## Naming
**Update 31 Oct 2026: the suite is now Velaria** (Velaria View / Canvas / Theatre / Stitch / Publish / Place). KALYX turned out to be an existing creative direction and AI production agency (Tokyo/Paris). Velaria comes from the velarium, the awning Romans stretched over amphitheatres. The rename note, shortlist and clearance to-dos are in "Velaria MVP and product roadmap". This log keeps the Kalyx name where it records what was built; the build itself (DeckLink display name, app label, macro IDs and folders, Notion project) still says Kalyx until the code rename.

### Earlier decision (28 Oct 2026)
Suite brand: **Kalyx** (from calyx, the cup that wraps a flower; suits 360, 180 and dome). Pattern is brand + plain function word:

| Function | Product name | Today (codename) |
|---|---|---|
| Insta360 batch stitching | Kalyx Stitch | Thimble |
| Place footage / text / 3D in the sphere | Kalyx Place: Footage · Text · 3D | Skylight_FactWindow / PIP, TextToSphere, SceneToSphere |
| Live headset preview + edit | Kalyx View (monitor) / Kalyx Canvas (in-headset control) | VR Link |
| Encode + YouTube metadata | Kalyx Publish | Orbit |

Rules: rename display names only for now; keep Fusion macro IDs (`Skylight_FactWindow` etc.) until the first installer, because comps, the headset Edit tab and the upgrade script key off them.

## Latency ("as close to real time as we can", Nelson 29 Oct)
Where the time goes for one parameter change: headset → bridge ≈ 1 ms; bridge SetInput ≈ 1–10 ms; **Resolve re-rendering the Fusion comp(s) at 5760² ≈ 200 ms (one card) to 1–2 s (several stacked comps)**; DeckLink → HEVC → headset ≈ 100–200 ms. The render dominates.
Done in v30: the headset no longer streams ~20 changes/s into Resolve during a drag (which queued stale renders and made the picture catch up only after release); it sends one change, waits for the resulting frame (bounded by 1.5× the last measured render time, 150 ms–2.5 s), then sends the latest hand position. Bridge: sets applied on receipt (not on a 70 ms tick); pan+tilt grabs go in under one comp lock (one render); the per-250 ms timeline scan (728 RPCs / 100 ms on Strange Worlds) replaced by a cached clip index rebuilt every 2 s; animated-input lookups cached.

- [ ] Measure: headset logs `Resolve updated in N ms` per change (adb logcat -s VRLink); bridge logs SetInput time per set.

## Footage tools in the headset (Nelson, 29 Oct: PanoMap / LatLong Patcher / stabilise / paint out nadir, zenith, tripod — with hand controllers; he has a splitter/combiner template in Resolve)
Nelson's call (29 Oct): LatLong Patcher only makes sense in-headset if painting works ("otherwise we may as well just do it in Fusion"); PanoMap re-orientation + a straight-horizon overlay is clearly useful.
**Finding (29 Oct, tested on a hidden scratch comp in Resolve 21.1.1, never a timeline comp):** Paint strokes *are* creatable from a script. A stroke is a `Stroke` tool chained into the Paint node's `Paint` input with `Points = {{X,Y,Time},…}` at tool level. Dead ends: Python `comp.Paste(dict)` fails on Fusion's `ordered()` tables; Lua `comp:Execute` / `fusion:Execute` do nothing from outside Resolve; `tool.LoadSettings(file)` on an existing Stroke applies inputs but drops Points. Working route: write a `.setting` file whose **first** tool is a throwaway and whose **second** tool is the stroke; `anyTool.LoadSettings(path)` applies the first to that tool and pastes the rest as new tools *with Points intact*; then connect `newStroke.Paint = previousStroke`, `Paint1.Paint = newStroke` from Python; delete the throwaway. Apply modes (`PaintApplyColor`, `PaintApplyRubThrough` with `.Offset`, clone) and brush size/softness are plain inputs. Points coordinate convention (centre-relative, likely in image-width units) still needs one calibration render. Nelson's template comp: MediaIn → Transform → Splitter → [LatLongPatcher Extract (90,0,0) AoV 90 → Paint → LatLongPatcher Apply] per eye → Merge over the plate → Combiner → MediaOut.
Tiers:
1. [x] **Expose existing Fusion tools** (v30): PanoMap and LatLongPatcher via a RegID whitelist in the bridge (`TOOL_INPUTS`); Transform / stereo splitter / Stabilizer can be added the same way.
2. [ ] **Patch workflow from the template**: headset "Patch" panel: pinch the spot on the sphere, set window angle/rotation; bridge generates the template chain on the clip under the playhead (nadir preset 90,0,0).
3. [ ] **Painting in the headset** (feasible, see finding): controller ray → sphere → patcher window (gnomonic from Rotate X/Y/Z + AoV) → stroke points; local ink preview drawn instantly, stroke committed as one Resolve round trip (not live ink: ~1–2 s per stroke with stacked comps). Rub-through/clone source set by pinching the source point. Brush size/softness/opacity on a Look tab. Scope it to nadir/tripod patches (5–20 strokes); detailed paint stays in Fusion.
Common need: an in-scene "drawing" mode (ray → sphere → equirect UV) and a visible cursor on the footage; the scene-pick code from v29 is the base.

## Black screens and loading-screen hangs — found and fixed (30 Oct 2026 evening, app 1.0.7+43 → +45)
Two separate bugs, both present in every build to date, both reproduced with Nelson in the headset and diagnosed from the collector log (`~/VRLink/logs/quest.log` on Bruce).
- **Black screen after the bridge connects** (every frame `xrEndFrame failed: -39`, POSE_INVALID; after 15 s the Quest's interstitial takes over). The compositor rejected the four *placed* panels restored from `settings.txt`: the file stores each quaternion at five decimals, which is a unit quaternion to us (|n²−1| < 2e-5 passed the v41 guard) and not to the compositor. Fix (+43): renormalise on restore and renormalise every layer's orientation right before submission; a frame that still fails now logs each layer's pose, norm to eight decimals, space, next pointer and sub-image. Nelson: "It's back!"
- **Stuck on the Quest loading screen after a quit until the headset is rebooted.** Android keeps a finished NativeActivity's process alive and runs the next launch in it on a new thread, over the same globals; the second run found the half-torn-down OpenXR instance and exited within 70 ms, so nothing ever rendered. Fix (+44): `android_main` ends with `std::_Exit(0)`; verified over adb that the process now dies on quit (`Process … has died`, activity force-removed). The relaunch itself still needs a head on (Guardian dialog blocks launches on a desk).
- Hover lift (+44): 4 px margin instead of 12, corner radius 18 (chips are 14), sheen 2 panel pixels tall whatever the chip width (it was 3 texels of a 160 px box scaled up — the "white line" on long chips). Not yet seen on-device.
- Test hooks (+45) in `cmd.txt`: `point <panel> <u> <v> [press]` aims a fake hand at panel texels (hover/press without hands; `point off` clears), `quit` takes the Quest-menu quit path. With `adb shell am broadcast -a com.oculus.vrpowermanager.prox_close` the session runs on a desk, but only until the Guardian dialog appears; `automation_disable` undoes it.
- Lesson for the readiness audit: the two worst alpha-killers were a text-file rounding and a process-lifecycle quirk, neither visible from the code and both found in minutes once the log collector was in place. `send-logs.sh` is therefore a day-one alpha deliverable, not a nicety.

### "Commit to Color page" for Kalyx Trim — design (not built)
Nelson, 2 Nov: "some kind of 'commit changes to Color page' that deletes the Fusion node while moving the items to a Color page node."

- **The API route exists:** `TimelineItem.SetCDL({"NodeIndex": "1", "Slope": "r g b", "Offset": "r g b", "Power": "r g b", "Saturation": "s"})` writes an ASC CDL into a node of the clip's Color-page graph — and an adjustment clip has its own graph, so the trim lands exactly where the Fusion node was. Then `DeleteFusionCompByName` (or leave the comp and set Amount = 0) removes the Fusion stage. One bridge command, one strip chip ("Commit to Color"), Resolve's undo covers it.
- **The mapping is a CDL, so it is exact for most of the bars and approximate for two.** CDL = `(in × slope + offset) ^ power`, then saturation. Gain → slope; Lift and Exposure → offset; Gamma → power = 1/gamma; Saturation → saturation; Temperature/Tint → per-channel slope (they are per-channel gains in the macro already). **Contrast** (pivot 0.5) folds into slope and offset exactly only when power = 1 — with Gamma and Contrast both moved, the committed look differs slightly from the Fusion one, because Fusion applies contrast after the gamma curve and CDL cannot express that order. Either accept and say so in the UI ("committed as a CDL; gamma + contrast together are approximate"), or commit gamma as power and contrast as a second node's slope/offset (`NodeIndex 2`), which is exact. Two nodes is the honest version.
- **Colour space:** Fusion runs in the timeline working space (RCM) and so does a Color-page node, so the numbers carry across without a transform. Verify on KALYX TEST with a scope read before and after (the regression rig can render frame 40 both ways and diff).
- **Order:** (1) prove `SetCDL` on an adjustment clip in KALYX TEST, (2) bridge `commit_trim` with the two-node mapping and a diff render, (3) strip chip. Half a day. Not before the Quest has been used with the plain Trim for a week — committing is a convenience; the trim itself is the feature.

## Known constraints
- Resolve scripting has no play/stop (seek only); no DCTL/OFX parameter access; re-render per change ~200–300 ms on a single card, 1–2 s with several stacked comps. From outside Resolve: `comp.Paste(dict)` and Lua `Execute` do not work; `tool.LoadSettings(file)` does (see footage tools). `fusion.NewComp(True, True)` gives a hidden scratch comp for experiments; close it without saving.
- Resolve's monitor raster tops out at 7680×4320; square 360 needs Output scaling ≤ 4320 (3840×3840 recommended).
- NDI from Python/C: `NDIlib_recv_create_v3` with colour format 1 (UYVY, BGRA with alpha) and bandwidth 100; a sender only delivers while its program monitor refreshes. libndi is loaded at runtime from NDI Tools (Video Monitor's `libndi_advanced.dylib` or the Adobe plug-in's `libndi.dylib`); nothing from the NDI SDK is shipped. The USB tether helper must map 47813 too, or the headset silently stays on Resolve.
